Solution architecture · proof of concept

ServeWell Printer Triage Agent

An agent that takes an incoming receipt- or kitchen-printer incident, looks up the facts about the store and the device, finds the right runbook steps, and either guides the store to a fix or packages the ticket for L2. Every step is checked, the ones that matter wait for a person, and everything is logged.

For the business owner

At a glance

Store managers wait 30–45 minutes at peak for a first useful answer, and 60–70% of tickets are known issues that already have a runbook. The pilot targets one of the most frequent of these: printers that go offline, print blank or garbled receipts, or aren't detected by the POS.

What the agent does

Reads the ticket, checks the store, device, warranty, SLA and known bugs, and pulls the matching runbook sections. It then decides: guide the store, ask for missing details, redirect a non-IT request, or escalate to L2 with the evidence already gathered.

What stays with a person

In the pilot's default supervised mode, every message to a store, every L2 escalation and every remote action waits for an analyst to click Approve. The agent only writes internal notes and sets routing on its own.

How we know it works

Every step shown to a store must be traceable to a specific runbook passage, or it is removed. The whole pipeline is scored against labelled historical tickets, and every run leaves an audit trail down to the exact prompt the model saw.

Architecture

System context

The agent is an orchestration layer. It holds no data of its own: it calls platform services for facts, knowledge and actions. For the POC, each platform building block is simulated locally with the ServeWell dataset, behind the same interface the real platform service would expose.

Orchestration

Agent workflow

The workflow is a fixed LangGraph state graph, not a free-form conversation between agents. Each node is a specialist with one job, reading and writing a shared, typed ticket state. Only one node calls the LLM. The rest are deterministic tools or guardrails, which makes the path reproducible and each decision explainable.

Worked example

One real run, end to end

This trace is from an actual run of the prototype on training ticket INC-00029: a Borivali store's Epson receipt printer isn't detected by the POS. Its history shows L1 had already asked the store to check the USB cable and power-cycle the printer.

Facts first. In 53 ms the enrich step confirmed the store and the asset (Epson TM-T88VI v1.12, under warranty to Feb 2027), noted that L1 had already tried something, and found other tickets for the same printer.

Knowledge next. Retrieval returned six chunks led by printer-offline.md. The runbook the ticket needed, pos-printer-integration.md, is filed under POS, which is why retrieval deliberately has no hard category filter.

One decision. The model chose guided L1 at 0.90 confidence and proposed six steps. It recognised that only a cable check and a power cycle had been done, so the POS printer-configuration path had not been tried yet. The labelled answer agrees.

The guardrail earned its keep. Step 5 cited a real chunk, but only 29% of its wording was supported there, so it was removed from the store message and shown to the reviewer instead. Five grounded steps went forward, and in supervised mode they wait for an analyst's approval before reaching the store.

Nearly all of the 38 seconds is the local 7B model. Every other step together takes well under a second.

Structured IT data

Tools, not reasoning, for facts

Anything that can be looked up is looked up. The model is never asked what version a printer runs, whether it's under warranty, or when the SLA expires.

The data service exposes store, asset, SLA, version-matrix and ticket-history lookups as SQL over DuckDB. The enrich step always runs every lookup: they cost milliseconds, and their results reach the model as "verified facts". When the requester's typed version disagrees with the CMDB, the CMDB wins and the mismatch is flagged. The same enrichment checks catch the dataset's deliberately broken tickets: all four false-asset tickets are flagged ASSET_NOT_FOUND.

The SLA clock is computed from the ticket's open time and the priority × category matrix (for example, P2: first response 30 min, L2 escalation by 90 min, resolution within 4 h). It appears in the work note and in the store message's promised update time.

RAG

Retrieval and grounding

How the knowledge base is indexed

  • Markdown is split on H2/H3 headings, so a chunk is a runbook section such as "Immediate Steps" or "Resolution Path B". Each chunk carries its heading path.
  • Sections are capped at 350 words. Header-only stubs merge into the next section; code fences and horizontal rules are handled.
  • The version matrix is indexed as one chunk per system, and is also queried directly as structured data.
  • Result: 49 documents → 667 chunks, each with doc type, category and section metadata. Embedding takes about 22 s.

How a query is answered

  • BM25 catches exact tokens: error codes like ERR-P502, versions, model numbers.
  • Dense search (nomic-embed-text in Chroma) catches paraphrase: "won't turn on" ≈ "startup failure".
  • Reciprocal Rank Fusion (k = 60, 40 candidates each) merges the two without comparing raw scores.
  • The top 6 chunks reach the model as numbered excerpts [C1]…[C6]. If embeddings are unavailable, retrieval degrades to BM25 and says so.

Grounding is enforced after generation, not requested in the prompt. Every step the model proposes goes through three tests before it can reach a store manager:

Hit@6 · all categories0.98A relevant doc is in the top 6 for 98% of the 220 labelled tickets
MRR · all categories0.91The first relevant doc is almost always ranked first
Doc recall@6 · Printers0.79Hit@6 1.00 on the Printers slice, measured during retrieval tuning
Doc recall@6 · all0.64Tickets list ~4.6 relevant docs, so top 6 caps recall; most misses are specs and SOPs

These numbers compare retrieval against each label's relevant_kb_docs, before any model is involved. Removing the soft category prior raised runbook recall on the POS + Printers slice from 0.68 to 0.75, because printer fixes also live in POS runbooks. The agent therefore runs without the prior.

Human in the loop

Actions and the autonomy line

The model can only suggest. It picks an automation from a closed list of three, and it cannot name an action. The policy layer turns the decision into proposed actions and decides which of them wait for a person. Supervised mode, on by default in the pilot, also holds back guidance that would otherwise be safe to send.

Approvals and rejections carry the reviewer's name into the audit log. Turning supervised mode off is how autonomy would be widened later, once evaluation supports it: confident, fully grounded guidance would then go straight to the store, while escalations and automations stay gated.

Correctness & reliability

Evaluation and observability

Before deployment: offline evaluation

  • The harness runs every Printers ticket (28 labelled, 14 guided / 14 L2, plus 7 unlabelled edge-case tickets) through the full graph in dry-run mode, with no ITSM writes.
  • Routing accuracy is reported twice, model-only and after policy, so the value added by the rules is visible.
  • Escalation recall is the safety number, because a missed escalation costs a store more than an unnecessary one. Escalation precision is the L2-workload number.
  • Also reported: grounding rate, retrieval recall@6 against labelled docs, human-review rate and seconds per ticket. The Evaluation page shows a confusion matrix and per-ticket drill-down.

After deployment: observability

  • An append-only audit log records every node with its latency, every action, and every approval or rejection with the reviewer's name.
  • Every run shows the exact LLM input, the raw JSON output, token counts and the prompt version (triage_resolve_v1).
  • Temperature 0 plus schema-constrained output make runs reproducible enough to compare prompt versions.
  • Operating KPIs to watch: reviewer override rate, grounding-failure rate, time to first response against SLA, and reopen rate on L1-closed tickets.
Decisions

Key trade-offs

DecisionChosenWhy, and what it costs
OrchestrationFixed LangGraph state graphExplicit, auditable path; typed state; branch for out-of-scope tickets. Costs flexibility compared with free-form multi-agent chat, which is not what an ITSM process needs.
LLM calls per ticketOne structured callHalves latency on a local 7B model compared with separate triage and resolve calls. Safety comes from the deterministic layers around it, not from a second model pass.
Modelqwen2.5:7b-instruct, localApache-2.0, free, private, good at JSON. Costs reasoning quality and time (≈35–60 s per ticket). One wrapper makes a hosted or platform model a configuration change.
RetrievalHybrid BM25 + dense, RRFExact error codes and paraphrase both matter in IT tickets. No hard category filter, because printer fixes span POS runbooks.
Store-facing textAssembled in code from grounded stepsNo ungrounded sentence can reach a store. Costs some fluency; only a short intro line is model-written.
AutonomySupervised by defaultTrust is earned with evidence. Costs analyst clicks during the pilot, which is exactly the review data needed to widen autonomy later.
ScopePrinters onlyDeep and defensible rather than broad and shallow. Other categories reuse the same graph (see below).
ObservabilitySQLite audit + in-app traceZero infrastructure for a POC. Production would use platform tracing (OpenTelemetry or Langfuse).

Adding a category (POS, Wi-Fi, Kiosks) reuses the graph, the data service, the retriever, the guardrails and the evaluation harness unchanged. What changes is configuration and content: the pilot category, the device list in the prompt, the scope keywords, and the automation allow-list. The enrichment already knows the expected asset type for all six categories, and the KB index already covers all 49 documents.

Candidly

Limits and next steps

Known limits

  • Latency. 35–60 s per ticket on a laptop, almost all of it model time. Acceptable against a 30–45 min baseline, but not instant.
  • Label coverage. Train labels contain only guided-L1 and L2 routes. The self-service, non-IT and needs-clarification paths are rule- and prompt-driven and are not statistically validated.
  • Small evaluation set. 28 labelled Printers tickets make the results directional. Full-run results are on the app's Evaluation page and aren't quoted here.
  • Observed bias. Tickets pre-flagged for escalation but with no troubleshooting history sometimes escalate when the label says guided L1 (e.g. INC-00031).
  • Heuristic grounding. The lexical check catches unsupported and invented content, but not a fluent paraphrase that subtly changes meaning.
  • Simulated systems. ITSM, notifications and automations are simulated, and there is no device telemetry in the dataset.

Next steps

  • Add an entailment or LLM-judge grounding check alongside the lexical one, scored against the labels' behaviour rubrics.
  • Tune how the pre-escalation flag is weighed against actual history, and re-measure escalation precision without losing recall.
  • Build a held-out test split and hand-labelled cases for the three unlabelled routes.
  • Widen autonomy by confidence band, using the pilot's approve/reject data as evidence.
  • Connect live printer status or telemetry so "is it online?" becomes a lookup, not a question for the store.
  • Roll out to the next category (POS offline) on the same graph.
